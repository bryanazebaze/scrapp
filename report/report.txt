DIAGRAM 1 — ARCHITECTURE GÉNÉRALE (4 PLANS)

Description:
  The overall system divided into 4 horizontal layers (plans), stacked
  vertically. Data flows top-to-bottom (collection → storage → API → client)
  with feedback loops for scheduling.

Layout:
  Draw 4 horizontal bands (full width), stacked with small gaps between them.
  Each band has a label on the left side (rotated 90° or in a side bar).
  Within each band, place component boxes left-to-right with arrows between them.

  Components (left to right):
    [Sources web] → [Adaptateurs dédiés (Mapiole, Kasastay)]
                  → [Adaptateur universel]
                  → [BaseFetchMixin (anti-bot: robots.txt, UA, délais, retries)]

    | sources | neighborhood_analytics | scheduler_jobs | image_cache (inutilisé)

Plan 3 — APPLICATION (band 3, green):
  Components (left to right):
    [FastAPI] ← routers: [annonces] [search] [neighborhoods] [admin] [health]

Plan 4 — CLIENT (bottom band, purple):
  Components (left to right):

      - go_router (navigation)

  Screens: Home (horizontal carousels) | Search | Property Detail | Favorites | Map | Neighborhood | Onboarding
  Arrows: Flutter → Dio → FastAPI endpoints
          CachedNetworkImage → original image URLs (direct from source sites)

Cross-plan arrows:
  Scheduler (Plan 3) → triggers adapters (Plan 1)
  Flutter (Plan 4) → HTTP → FastAPI (Plan 3)
  FastAPI (Plan 3) → SQL → PostgreSQL (Plan 2)

DIAGRAM 3 — MODÈLE DE DONNÉES (ER DIAGRAMM)

Description:
  Entity-Relationship diagram showing all 8 tables, their columns (key ones

DIAGRAM 4 — FRAMEWORK DE SCRAPING (HIERARCHIE ADAPTATEURS)
================================================================================

Description:
  Class hierarchy showing the SourceAdapter ABC, BaseFetchMixin, and the
  concrete adapters. Shows the interface contract and how anti-bot is shared.

Layout:
  Draw a UML-style class diagram with inheritance and mixin arrows.

Classes:

  SourceAdapter (ABC, abstract base):
    Location: top-center
    Attributes:
      platform_slug: str
      base_url: str
      adapter_kind: str ("dedicated" | "universal")
      source_id: Optional[int]
    Methods (abstract):
      fetch_listings(max_pages) → list[RawListingDraft]
      fetch_details(listing_url) → Optional[RawListingDraft]
      normalize_data(raw: dict) → RawListingDraft
    Methods (concrete):
      validate_data(draft) → (bool, list[str])
      scrape(max_pages) → list[RawListingDraft]  (delegates to fetch_listings)

  BaseFetchMixin (mixin, left of SourceAdapter):
    Location: top-left
    Attributes:
      request_timeout: int = 15
      max_retries: int = 3
      session: requests.Session
      _user_agent: str (from pool of 5 browser UAs)
      _robots: RobotFileParser
    Methods:
      init_fetch(base_url, crawl_config)
      fetch(url) → Response | None   (with robots.txt check)
      fetch_text(url) → str | None
      head_ok(url) → bool
      _polite_sleep()  (jittered delay: settings.scraper_delay_range)
      _default_headers() → dict  (browser-like headers)
      _load_robots() → RobotFileParser | None
      _robots_allows(url) → bool
      _resolve_proxies() → dict  (env or per-source config)
    Anti-bot features (label these as a callout box):
      - Browser-like User-Agent (random from pool)
      - robots.txt respected
      - Jittered delays between requests
      - Session reuse with cookies
      - Retries with exponential backoff (429/5xx)
      - Optional outbound proxy
      - 15s timeout

  MapioleAdapter (concrete, bottom-left):
    Inherits: SourceAdapter, BaseFetchMixin
    platform_slug = "mapiole"
    adapter_kind = "dedicated"
    Notes: Auto-promotes all listings (no confidence gating)

  KasastayAdapter (concrete, bottom-center):
    Inherits: SourceAdapter, BaseFetchMixin
    platform_slug = "kasastay"
    adapter_kind = "dedicated"
    Notes: Auto-promotes all listings

  UniversalAdapter (concrete, bottom-right):
    Inherits: SourceAdapter, BaseFetchMixin
    platform_slug = "universal"
    adapter_kind = "universal"
    Notes: Confidence-gated (≥0.75 auto, 0.40-0.74 pending, <0.40 rejected)
    Extra pipeline stages: URL discovery → card detection → field extraction → confidence

  RawListingDraft (dataclass, shown as a separate box, connected to SourceAdapter):
    Fields: url_source, title_raw, price_raw, price_parsed, currency,
            location_raw, description_raw, property_type_raw, images_raw,
            bedrooms, bathrooms, area_sqm, confidence, payload

Arrows:
  MapioleAdapter --|> SourceAdapter (inherits)
  MapioleAdapter --|> BaseFetchMixin (mixin)
  KasastayAdapter --|> SourceAdapter
  KasastayAdapter --|> BaseFetchMixin
  UniversalAdapter --|> SourceAdapter
  UniversalAdapter --|> BaseFetchMixin
  SourceAdapter --uses--> RawListingDraft (returns)

DIAGRAM 5 — PIPELINE D'INGESTION (IDEMPOTENT FLOW)
================================================================================

Description:
  Flowchart showing how a RawListingDraft moves through the ingest pipeline.
  The key decision: is this URL already in the DB (re-crawl) or new?
  Shows the idempotency mechanism (url_hash) and the append-only history.

Layout:
  Top-to-bottom flowchart with decision diamonds and process boxes.

Flow:

  Start: [RawListingDraft from adapter]
    ↓
  [Compute url_hash = sha256(url_source)]
    ↓
  Decision: {url_hash exists in raw_listings?}
    │
    ├─ YES (RE-CRAWL path):
    │   ↓
    │   [Fetch existing raw_listing row]
    │   ↓
    │   [Fetch latest listing_history event for this raw_listing]
    │   ↓
    │   Decision: {price or availability changed?}
    │     │
    │     ├─ YES → [Append new listing_history event (price_change / availability_change)]
    │     │         [Update canonical.last_seen_at]
    │     │         [Update canonical.current_best_price if lower]
    │     │
    │     └─ NO → [No-op, skip]
    │   ↓
    │   [stats.recrawl += 1]
    │
    └─ NO (NEW LISTING path):
        ↓
      [Resolve location_id from location_raw (detect_city + detect_neighborhood)]
        ↓
      [Compute match_key = sha1(type | city_slug | neighborhood_slug)]
        ↓
      Decision: {match_key is None (no city parsed)?}
        │
        ├─ YES → [Synthesize unique key: "noloc:" + sha1(url)]
        │
        └─ NO → continue
        ↓
      [Query all canonical_properties with same match_key (candidate set)]
        ↓
      Decision: {candidates exist?}
        │
        ├─ NO → [Classification = "New Property", DCS = 0.0]
        │
        └─ YES → [Compute DCS for each candidate]
                 [Pick best DCS + best title_sim]
                 ↓
               Decision: {title_sim >= 80?}
                 ├─ YES → [Confirmed Match → link to existing canonical]
                 └─ NO → Decision: {DCS >= 0.65?}
                          ├─ YES → [Probable Match → link]
                          └─ NO → [New Property → create canonical]
        ↓
      [Determine review_status]:
        Decision: {adapter_kind?}
          ├─ "dedicated" → review_status = "auto_promoted"
          └─ "universal" → Decision: {confidence?}
                  ├─ < 0.40 → "rejected" (skip, do NOT insert raw_listing)
                  ├─ 0.40-0.74 → "pending" (insert raw_listing, canonical_property_id=NULL)
                  └─ ≥ 0.75 → "auto_promoted" (insert raw_listing + link/create canonical)
        ↓
      [Insert raw_listing row (immutable)]
        ↓
      Decision: {review_status == "auto_promoted"?}
        ├─ YES → [Append listing_history "first_seen" event]
        └─ NO → [No history event (pending awaits human review)]
        ↓
      [stats.new += 1]

  End: [db.commit()]

Key annotations on the diagram:
  - url_hash = sha256(url_source) → idempotency key
  - raw_listings is NEVER updated after insert
  - listing_history is APPEND-ONLY
  - Pending listings do NOT create canonical properties (prevents orphans)
  - mark_removed() runs post-crawl: any raw_listing not seen this session → "removed" event

Layout:
  UML sequence diagram with lifelines (vertical dashed lines) and horizontal

Lifelines (left to right):
  APScheduler | main.py (orchestrator) | SourceAdapter | core/ingest.py | PostgreSQL

Messages (top to bottom):

  APScheduler → main.py: trigger (daily 02:00 or manual CLI or API)

          SourceAdapter → SourceAdapter: parse cards, extract fields

            SourceAdapter → Internet: GET detail page
            Internet → SourceAdapter: HTML response

            SourceAdapter → SourceAdapter: validate_data (title + price/location + images)

DIAGRAM 7 — RÉSOLUTION DES DOUBLONS (DCS DECISION TREE)
================================================================================

Description:
  Decision tree for the Duplicate Confidence Score (DCS) computation and
  classification. Shows the 7 weighted factors and the 3 outcome classes.

Layout:
  Two parts:
  Part A (top): The factor weights as a formula/weighted-sum box.
  Part B (bottom): The decision tree with classification thresholds.

Part A — DCS Formula:

  Draw a box with the formula:
    DCS = 0.30 × title_sim
        + 0.20 × price_proximity
        + 0.15 × type_match
        + 0.15 × surface_match
        + 0.10 × bedrooms_match
        + 0.05 × location_sim
        + 0.05 × image_overlap

  Below each factor, a small annotation:
    title_sim: rapidfuzz token_set_ratio (0-1). 0.30 weight — DOMINANT factor.
    price_proximity: 1 - |Δp|/max(p1,p2). 0=very different, 1=identical. Neutral 0.5 if missing.
    type_match: 1.0 if exact match, 0.0 if different. Neutral 0.5 if either missing.
    surface_match: 1.0 if within 15% tolerance, 0.0 otherwise. Neutral 0.5 if missing.
    bedrooms_match: 1.0 if exact, 0.0 if different. Neutral 0.5 if missing.
    location_sim: 1.0 if same location_id, else title_sim of raw strings. Neutral 0.5.
    image_overlap: Jaccard of image URL hashes. Usually 0.5 (neutral) cross-source.

Part B — Decision Tree:

  Start: [New draft + candidate canonical (same match_key)]
    ↓
  [Compute title_sim = rapidfuzz.token_set_ratio(normalized titles)]
    ↓
  Decision: {title_sim >= 80?}
    │
    ├─ YES → [Classification: Confirmed Match]
    │         [auto_promote = True]
    │         [Link draft to existing canonical_property]
    │
    └─ NO → [Compute DCS (weighted sum of 7 factors)]
             ↓
           Decision: {DCS >= 0.85?}
             │
             ├─ YES → [Classification: Confirmed Match]
             │         [auto_promote = True]
             │         [Link to canonical]
             │
             └─ NO → Decision: {DCS >= 0.65?}
                      │
                      ├─ YES → [Classification: Probable Match]
                      │         [auto_promote = True]
                      │         [Link to canonical (with explanation)]
                      │
                      └─ NO → [Classification: New Property]
                               [auto_promote = False]
                               [Create new canonical_property]

  Annotation: match_key = sha1(property_type | city_slug | neighborhood_slug)
  It is a CANDIDATE-RETRIEVAL bucket, NOT a unique identifier.
  Multiple distinct properties in the same type+city+neighborhood share a key.

DIAGRAM 8 — SCRAPER UNIVERSEL (4-STAGE PIPELINE)
================================================================================

Description:
  The universal adapter's 4-stage pipeline: URL discovery, card detection,
  field extraction, and confidence scoring. Shows the extraction priority
  (JSON-LD > OpenGraph > heuristic) and the 3-way gating outcome.

Layout:
  Horizontal pipeline (left to right) with 4 large stage boxes.
  Each stage has sub-components inside.

Stage 1 — DÉCOUVERTE D'URL (left):
  Inputs: seed_url (from sources.site_url)
  Sub-components:
    [Sitemap parsing] — try /sitemap.xml, extract listing URLs
    [Link crawling] — follow links matching LISTING_PATH_RE
                      (paths containing: property, listing, annonce, immobilier, etc.)
    [Pagination] — follow "next" links, page=N patterns
    [Filter] — exclude UTILITY_PATH_RE (login, register, contact, about, blog, etc.)
  Output: candidate detail-page URLs

Stage 2 — DÉTECTION DE CARTES (center-left):
  Input: candidate URLs
  Sub-components:
    [Fetch HTML] (via BaseFetchMixin.fetch)
    [Parse DOM] (BeautifulSoup)
    [Card detection heuristics] — find repeated DOM structures that look like
      property cards. Signals (3-of-5 required):
        1. Repeated signature (same tag structure repeated ≥3 times)
        2. Contains <img> tag
        3. Contains a link (<a href>) to a detail page
        4. Contains price-like text (XAF, FCFA, CFA + digits)
        5. Contains a city/neighborhood keyword
    [Extract detail URLs from cards]
  Output: confirmed detail-page URLs (from detected cards)
  Note: Non-card URLs are skipped (reduces false positives)

Stage 3 — EXTRACTION DE CHAMPS (center-right):
  Input: detail-page URL
  Sub-components (priority chain, top = highest priority):
    [JSON-LD extraction] — look for <script type="application/ld+json">
      with @type Product/Offer/Residence → extract price, images, title, etc.
      f_schema = 1.0
    ↓ (if no JSON-LD)
    [OpenGraph extraction] — meta tags: og:title, og:image, og:description, etc.
      f_schema = 0.5
    ↓ (if no OG)
    [Heuristic extraction] — CSS selectors + regex for common patterns
      f_schema = 0.0
  Output: extracted fields dict (title, price, images, location, etc.)

Stage 4 — SCORE DE CONFIANCE (right):
  Input: extracted dict + from_card flag + images_resolvable + url_source
  Formula:
    confidence = 0.40 × f_schema + 0.20 × f_struct + 0.15 × f_price
               + 0.10 × f_images + 0.10 × f_location + 0.05 × f_source
  Factor details:
    f_schema: 1.0 (JSON-LD) | 0.5 (OG) | 0.0 (heuristic)
    f_struct: 1.0 if from detected card, 0.0 otherwise
    f_price: 1.0 if price_parsed > 0
    f_images: 1.0 if ≥1 image URL resolves (HEAD 200)
    f_location: 1.0 (known city) | 0.5 (known neighborhood) | 0.0
    f_source: 1.0 if domain in CAMEROON_RE_DOMAINS allowlist
  ↓
  Decision: {confidence value?}
    ├─ ≥ 0.75 → [auto_promoted] → create/link canonical property
    ├─ 0.40-0.74 → [pending] → insert raw_listing, await human review
    └─ < 0.40 → [rejected] → do NOT insert raw_listing

  Output: RawListingDraft with confidence score → sent to ingest pipeline

DIAGRAM 9 — PIPELINE ANALYTIQUE
================================================================================

Description:
  The analytics computation pipeline: how raw data (canonical_properties +
  listing_history) is transformed into neighborhood scores and cached in
  neighborhood_analytics. Shows the 5 score functions and their inputs.

Layout:
  Left-to-right data flow with a "computation" section in the middle
  and the cache table on the right.

Inputs (left side, two boxes):
  [canonical_properties]
    → current_best_price, property_type, location_id, area_sqm
  [listing_history]
    → first_seen events (for days-on-market, trend, activity)
  [locations]
    → city, neighborhood (grouping key)

Computation (center, large box labeled "core/analytics.py + core/scoring.py"):

  Sub-step 1: Aggregate raw stats per location (+ optional property_type):
    - prices = sorted([current_best_price for canonicals in location])
    - avg, median, min, max, price_per_sqm
    - median_days_on_market (from first_seen → removed duration)
    - trend_pct (90-day price change: recent vs prior window)
    - listings_per_week (first_seen events / weeks in window)
    - top_decile_share (fraction ≥ 1.5× city median)
    - amenity_share (fraction mentioning pool/garden/garage/terrace in payload)
    - city_median_price (for premium normalization)

  Sub-step 2: Compute 5 scores (0-10 scale):

    [premium_score]
      Input: neighborhood_median, city_median
      Formula: min(10, 5 + (ratio - 1) × 2.5) where ratio = median/city_median
      Output: 0-10 (5=par, 7.5=2× city, 9=3× city, capped at 10)
      Label: Premium / Upscale / Mid-tier / Affordable

    [demand_score]
      Input: median_days_on_market
      Formula: 10 - 3.5 × log10(days/3)
      Output: ~8.7 for 7 days, ~6.5 for 30 days, ~4.8 for 90 days
      Label: High / Moderate / Low Demand

    [growth_score]
      Input: trend_pct (90-day price change %)
      Formula: 5 + trend_pct/4, clamped [0, 10]
      Output: 5=flat, 8=+20%, 2=-20%

    [activity_score]
      Input: listings_per_week
      Formula: 10 × (1 - exp(-per_week/5))
      Output: ~2 for 1/wk, ~5 for 5/wk, ~9 for 20/wk (saturating)

    [luxury_score]
      Inputs: premium_score, top_decile_share, amenity_share
      Formula: 0.50×premium_norm + 0.30×top_decile + 0.20×amenity (renormalized)
      Output: 0-10 blend

  Sub-step 3: Trend classification:
    trend_direction = "up" if trend > 1% | "down" if < -1% | "flat"

Output (right side):
  [neighborhood_analytics] (cache table)
    Columns: location_id, property_type, period,
             listing_count, average_price, median_price, min_price, max_price,
             price_per_sqm, premium_score, demand_score, growth_score,
             activity_score, luxury_score, trend_direction, trend_pct, computed_at

  Upsert: recompute_all() overwrites existing rows (same location+type+period)
  Schedule: weekly Monday 03:00 UTC (or manual: python cli.py analytics)

Feedback arrow:
  API endpoint GET /neighborhoods/{slug} reads from neighborhood_analytics cache
  (not recompute on every request).

DIAGRAM 11 — MACHINE À ÉTATS DU REVIEW
================================================================================

Description:
  State machine for raw_listings.review_status, showing all states and
  the transitions between them (with their triggers).

Layout:
  State diagram with nodes (rounded rectangles) and directed edges (arrows)
  labeled with the trigger action.

States (nodes):

  [pending] (yellow/grey)
    Description: Universal-scraper listing with confidence 0.40-0.74.
    canonical_property_id = NULL (no canonical created yet).
    Listed in admin review queue.

  [auto_promoted] (green)
    Description: Dedicated source (always) or universal with confidence ≥ 0.75.
    canonical_property_id is set (linked to existing or new canonical).
    first_seen history event appended.

  [human_approved] (blue)
    Description: Admin approved a pending listing via POST /admin/review/{id}.
    canonical_property_id is set (matcher re-run, create or link canonical).
    first_seen history event backdated to crawled_at.

  [rejected] (red)
    Description: Either:
      - Universal scraper confidence < 0.40 (rejected at ingest, NOT inserted)
      - Admin rejected a pending listing (raw_listing stays for audit, never promoted)

Transitions (arrows):

  Ingest pipeline (adapter_kind = "dedicated"):
    [start] → [auto_promoted]
    Label: "dedicated source, always auto-promote"

  Ingest pipeline (adapter_kind = "universal"):
    [start] → [rejected]
    Label: "confidence < 0.40 (not stored)"

    [start] → [pending]
    Label: "0.40 ≤ confidence < 0.75"

    [start] → [auto_promoted]
    Label: "confidence ≥ 0.75"

  Admin review:
    [pending] → [human_approved]
    Label: "POST /admin/review/{id} action=approve"

    [pending] → [rejected]
    Label: "POST /admin/review/{id} action=reject"

  Re-review (edge case):
    [auto_promoted] → [human_approved]
    Label: "POST /admin/review/{id} action=approve (re-confirm)"

  No transitions FROM:
    [rejected] — terminal state, no further action
    [human_approved] — terminal state (promoted)

Post-promote actions (annotations on the [human_approved] node):
  - Re-run matcher (find_canonical_match)
  - Link to existing canonical OR create new canonical
  - Set review_status = "human_approved"
  - Backdate first_seen listing_history event to raw_listing.crawled_at

Review queue endpoint:
  GET /admin/review/pending → lists all raw_listings WHERE review_status = "pending"
